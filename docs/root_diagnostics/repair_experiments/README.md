# 冲突修复补列模块：第一版实际结果

结论：在40任务、第25轮的434条整数不可行列上，单纯三轮局部变体补列尚未恢复可行；增加小范围原MILP联合修复后得到利润238，再做小范围利润改进取得305.83。全部新列和最终整数witness通过独立数据级检查。没有证明原问题最优，没有取得严格公平性能优势的证据。

## 使用

```powershell
experiments/.venv/Scripts/python.exe code/dwcg/repair_pool.py --output <新的结果目录>
experiments/.venv/Scripts/python.exe code/dwcg/repair_pool.py --iteration 25 --no-joint --output <另一新目录>
```

IDE中打开脚本，填写运行参数`--output <新的结果目录>`；默认输入为封存的40任务根证书第25轮，无需重跑CG。`--time-limit`默认30秒软预算，`--rounds`默认3轮，每轮新列上限200。支持API `repair(data, pool)`，返回结果及独立扩充列池。只适用于根节点，CLI拒绝忽略非空分支限制。当前作为独立修复模块，尚未接入主CG/B&P循环；现有模型和V0–V3入口未改动。

## 实现

1. 原列池整数恢复，保留任何经过验证的已有incumbent。
2. 保持每站恰选一列，最小化全局行的弹性违约总量；在不增加该违约量的条件下最大化原经济利润。两次求解状态分别保存；第一步未证明最优时不宣称词典序全局最优。
3. 冲突定向生成重复任务删除、前驱插入、前驱交换、可选后继闭包删除列，再生成有界的单任务删除及模式变体。必做任务和其祖先受到闭包删除保护。单任务删除只是候选，是否补齐必做由真实整数主问题决定。
4. 每条候选重算配置、时间、疲劳和原利润，局部校验后去重追加。全部旧Column对象和调用者原列池不修改。不要求新列检验数为正：它们用于整数拼接，不承担精确定价证明。
5. 扩充池按全部原全局约束及真实利润求整数解；人工变量不参与此步骤。失败不判原问题不可行。
6. 无可行解时，释放冲突附近最多4个站的原x变量；其他站x固定为候选分配，原Compact的任务、优先、回收、资源、局部约束全部保留。若产生可行解，提取工作站配置作为新列。
7. 可行后分线释放最多3个活动站和1个空站，以原净利润做局部改进，每线最多4秒。始终保留已验证最好解；超时或失败不能降低LB。

联合修复直接调用CPLEX求小范围Compact模型，是本算法真实组成部分，时间全部计费；不是仅靠原列池整数恢复取得的效果。当前每次仍完整建立Compact再固定非邻域x，未来可优化建模，但本轮未改模型。

局部列合法性由make_column/validate_column检查；整数witness通过原Compact约束与独立数据级验证。原IP最优标志始终false，修复模块只提供LB。固定站可能使邻域不可行，这仅表示本次邻域失败。没有改变精确定价、UB与安全剪枝逻辑。要加入完整B&P节点，仍需显式传递并检查节点限制，当前不支持该扩展。

round25_quality：第一轮新增54列，种子总违约2；第二轮新增10列，种子违约1；第三轮新增6列，种子违约1。三次真实受限IP仍证明不可行。联合修复新增3列，恢复利润238；L1局部利润改进无改善，L2局部改进新增3列，将利润升至305.83。434→510列。详细求解状态、候选分配、违约行、每条新列来源、自由站集合和最终分配均保存在result.json/allocation.txt。

因此本次有效性依赖小范围联合修复；不能声称简单删任务就解决了问题。局部生成的70列使违约量下降，但没有独立形成可行组合。305.83是可行利润，不是已知最优值。

预算以读取已保存列池后的修复调用为起点，不含生成原列池成本、Python启动/导入、最终结果落盘。原封存无Compact运行生成列池本身约15.37秒，因此不能把修复11.14秒与Compact15秒直接比较。此前独立Compact的305.43也只是其限时incumbent，不能用0.40利润差宣称算法胜出。这里只是单实例功能实验，没有多seed性能结论。

## 验证

`tests_final_v3.txt`记录最终源码26项回归（6项修复、5项不可行诊断、6项根诊断、9项B&P），全部PASS。覆盖重复消除、补前驱、局部可行性、候选去重与上限、输入列池隔离、固定站联合修复、原问题不可行、极短时限、保留incumbent及原B&P证明回归。

`experiments/verify_repair_experiments.py`独立重建本次四个成功完成运行的原始池及追加序列，以Task01独立pattern算术验证所有新增列，检查重复与总数、所有witness的全局可行性和利润、最终witness属于扩充池，以及LB不下降。结果见`independent_validation.json`：四个运行均PASS；无联合恢复运行无witness，检查范围仅为合法新列及无误报。

完整列枚举对照由已有小规模根/B&P回归覆盖，本轮没有枚举40任务的指数列域。未重跑116份历史搜索；未引入RL；未合并main。

建议下一步：将模块接到根CG的预算钩子，比较“无修复/纯补列/补列+联合修复”从生成列开始的完整总预算，先多seed复验。根据现有结果，应优先改善修复邻域选择及候选列多样性，暂不把纯删除策略视为充分方案。
